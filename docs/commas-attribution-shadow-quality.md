# Commas attribution shadow quality

The report at `/reports/commas-attribution` is a read-only measurement surface. Its authenticated GET API derives the organization from the server session, requires `connectors.view`, and resolves exactly one connected Commas connection and active provider account. It reads normalized observations, immutable Evidence **metadata only**, Journey shadow-event metadata, exact canonical orders, and Everflow conversion/click identities. It never reads raw Evidence payloads or writes source tables or attribution credits. The response contains counts and field names, not checkout parameter values.

The valid purchase cohort consists of `commas` / `product.purchased` observations. A persisted attribution delivery and Evidence reference are accepted-path evidence: the Worker verifies signatures before those writes. Rejected unsigned or malformed requests are not durably counted today; the report shows these as unavailable rather than zero. Duplicate deliveries and reconciliation executions do not add purchases because observations are unique by provider event identity.

Exact commerce identity is separate from marketing evidence. `payment_public_transaction_id` must match the ORD syntax and resolve through the same organization, connection, and provider account to `commas_public_transaction` and then a canonical order. Affiliate, sub-ID, and transaction-alias presence are measured independently. A missing field is never counted as a disagreement. Stored Everflow comparison is preserved alongside a current read-only comparison; later Everflow ingestion can change current availability without rewriting the historical observation. A unique Everflow identity shape is required for field comparison. The known conflict is a populated `sub4` disagreement: transaction identity, affiliate ID, and `sub1` agree, while Commas aliases agree internally. Conflict diagnostics contain only field names and agreement states. The 26 current no-TID purchases have exact commerce identities but no provider marketing fields; the report never calls them attributed. Processor/payment-path segmentation is unavailable because normalized `payment_type` is not a trustworthy processor identifier.

Immutable Evidence `normalizer_version` identifies the original live normalizer. An Evidence v1 record whose observation is now v2 is an Evidence-reconciled derivation; v2 Evidence identifies natural live normalization. The report also counts later derived reconciliation. These cohorts must remain visible separately. The provider event timestamp drives UTC daily grouping; immutable delivery `observed_at` drives latency and post-cutover measurement. ORD mapping `created_at` approximates first identity availability. Initial match state and first exact-match latency cannot be reconstructed reliably from the current mutable observation schema, so the report does not invent those numbers.

The future sample gate is **500 distinct clean post-cutover product purchases or seven full healthy measurement days**, whichever comes first. A tenant/provider-scoped append-only measurement epoch is seeded from the first restricted v2 Evidence delivery after the verified 25365-only cutover (`2026-09-13 23:43:33.814797 UTC` for the current scope). This is a conservative evidence-backed measurement start, not a guessed deletion instant and not attribution truth. The epoch retains its Evidence reference and recording actor. Only distinct v2 provider event observations with delivery on or after that epoch count toward the 500-purchase gate; historical Evidence reconciliations do not. A healthy UTC day must be later than the epoch's calendar day, fully elapsed, and have an append-only certification containing endpoint health, provider transaction parity, ingestion, ORD, Journey, and firewall evidence references. There is no durable complete-day certification yet, so the healthy-day count is zero; no historical day is silently certified. A separate audited operational certification path is needed prospectively. Reaching the gate permits only a separate attribution-precedence design review.

Future alerts should evaluate sustained ORD match degradation, alias conflict growth, Everflow conflict growth, provider transactions without purchases, stale transaction ingestion while webhooks continue, and Journey lag. No thresholds or production alerts are activated by this milestone. Any unexplained conflict, significant no-TID cohort, systematic payment-path difference, ingestion instability, or firewall regression must be called out before the design review even if the numerical sample gate is reached.

The scorecard now uses a `STABLE`, `SECURITY INVOKER`, service-role-only SQL aggregate. It returns counts and daily groups, never all observation rows, so it has no 5,000-observation application cutoff. Conflict details use a separate 50-row bounded function. Both functions only SELECT and enforce organization, connection, and provider-account scope; the GET route gets organization from the authenticated server session. Current production EXPLAIN for the scoped observation/Evidence join returned 116 observations in 1.087 ms, using a small observation scan and indexed Evidence lookups. The Everflow conversion lookup has no dedicated `(organization_id, transaction_id)` index in the inspected schema; revisit the plan as the cohort grows. No speculative index was added. This migration and page have not been deployed in this workstream.
